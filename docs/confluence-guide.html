NR Monitor – Automatic bug fixing from New Relic alerts

In one line: when New Relic sees serious errors in one of our apps, Claude automatically finds the bug, fixes it, tests the fix on a safe copy with dummy data, opens a Pull Request and posts a short report in Slack. A developer reviews and merges. Nobody has to start it.

Status: tested end-to-end (New Relic alert → service → Claude → fix PR + Slack report in ~2 minutes). Waiting for an always-on server to go live.

1. How it works

 New Relic                 NR Monitor service             Claude Code + nr-monitor plugin
 (watches the app)         (small program on a server)    (does the investigation)
 ─────────────────         ───────────────────────────    ───────────────────────────────
 Error rate high  ──alert──►  checks secret + priority  ──►  reads New Relic errors + logs
 or fatal log      webhook    puts job in a queue            finds the cause in the code
                              downloads the project          writes a test + the fix
                              starts Claude                  proves it on a local copy (dummy data)
                              deletes the copy after         opens a PR, posts to Slack
  1. New Relic sees a problem (for example error rate above 10% for 5 minutes) and sends an alert to the service.
  2. The service checks the alert is real (secret), important (High or Critical) and not a repeat. It puts it in a queue.
  3. When it is its turn, the service downloads a fresh copy of the project into a temporary folder and starts Claude there.
  4. Claude (with our plugin) investigates and, if it is a genuine bug, opens one PR and posts a report with before/after proof in Slack. If it is not a bug, it only reports that.
  5. The service deletes the temporary copy. Nothing of the project stays on the server.

Besides alerts, the service also checks every project every 12 hours, to catch problems that never triggered an alert.

4. Safety rules

  • Never merges. Claude only opens PRs; a developer reviews and merges. Branch protection on main backs this up.
  • Read-only database. Only a read-only database URL is used, and the tool forces read-only transactions.
  • Dummy data only for testing fixes. Never calls real Salesforce, production databases, real email or SMS.
  • Secret on the webhook. Alerts without the correct secret are rejected. Large requests (over 100 KB) are rejected.
  • Keys never in Git or chat. They live only in files on the server.
  • No project copies kept. Each run uses a temporary copy that is deleted afterwards.
  • No client names in the plugin, examples or docs.

7. Add a project

  1. Give the GitHub account Write access to the repo (or use a token, section 8).
  2. Add the project to projects.json and create envs/<app>.env.
  3. Restart: sudo systemctl restart nr-monitor
  4. From a laptop, inside the project folder (its .env has the New Relic keys), create the alert rules and the webhook:
( printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"terminal","version":"1"}}}' \
  '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"nr_setup_alerts","arguments":{"service_url":"https://nr-monitor.company.com"}}}'
  sleep 20 ) \
| NR_MONITOR_SECRET='<the webhook secret>' \
  node ~/claude-nr-monitor/plugins/nr-monitor/mcp/server.js \
| grep '"id":2'

Expected: "Created webhook + workflow: High/Critical alerts … go to the nr-monitor service".

What this does: it calls the plugin's nr_setup_alerts tool directly. printf sends the three messages Claude would send; sleep 20 gives it time to finish; NR_MONITOR_SECRET is stored in the New Relic webhook so New Relic sends it with every alert; grep shows only the result. Alternative: in Claude Code inside the project, run /nr-monitor:setup.

Running it again does not change existing alert rules or webhooks. To point a project to a new address or secret, first delete its destination "Claude agent → service (<app>)" in New Relic → Alerts → Destinations.

8. Client repos (GitHub token per project)

If the server's GitHub account cannot get access to a client repo, use the token of a developer who already has Write access there:

  1. The developer creates a classic token, scope repo only, with an expiry date. If the client uses SSO: Configure SSO → Authorize for the client organization.
  2. Check it on the server: GH_TOKEN=<token> gh api repos/<owner>/<repo> --jq .permissions.push must print true.
  3. Add GITHUB_TOKEN=<token> to that project's envs/<app>.env and restart the service.
  4. Before it expires, create a new token and replace it.

The token is used only for that project (clone, branch, PR). It is never written into the project copy and is hidden in error messages. PRs show the developer's name. Confirm with the client that automated use is allowed.

11. Known limits

  • The waiting queue is kept in memory. If the service restarts, waiting alerts are lost (the 12-hour check catches them later). A fix is planned.
  • Without DATABASE_URL_READONLY, Claude cannot check data and says so in the report.
  • The same bug coming back after New Relic closed the issue starts a new run (new issue id). If a fix PR is already open, Claude reports that instead of opening another.

12. FAQ

Does it cost tokens all the time? No. Claude only runs on High/Critical alerts and once per project every 12 hours.

Can it break production? No. It only reads production data (read-only), tests on dummy data, and only opens PRs.

Does it keep our code on the server? No. Each run uses a temporary copy that is deleted afterwards.

What if production is down? Outages, Salesforce errors and validation rejections are reported as "not a bug"; Claude does not try to "fix" them.

Who reviews the PR? The developers of that project, like any other PR.
